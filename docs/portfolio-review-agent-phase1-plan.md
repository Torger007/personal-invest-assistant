# 持仓复盘 Agent 一期实施方案

> 状态：方向已确认，待实施  
> 制定日期：2026-10-13  
> 适用分支：`develop`  
> 范围：当前用户的真实基金持仓；由用户手动发起复盘

## 1. 目标

第一期只完成一个用户任务：

> 分析我的当前持仓，告诉我今天最值得关注的三件事，并解释与上次判断有何变化。

交付物是一份可保存、可回看、可核对证据的持仓复盘报告。Agent 根据当前持仓、最近可用的基金与市场数据、已有规则建议、用户确认过的偏好和上一次成功复盘完成分析。用户能够从报告中的结论打开对应持仓、建议或历史报告。

“今天”指本次复盘的日期，不表示基金净值已更新至当天。报告分别标注持仓估值、基金净值、市场数据及规则建议的实际截至时间。第一期沿用现有 OpenAI / Anthropic Provider 和服务端受约束 Agent 架构。

## 2. 当前基础与先行修正

项目已具备真实持仓、基金净值、市场与板块数据、单基金规则建议、受约束规划、工具输入校验、数据质量门、SSE 进度、用户隔离和 Agent 历史记录。第一期在这些模块上扩展，不另建一套执行框架。

实施前必须核对并修正以下数据口径与接口问题：

1. `get_user_portfolio` 当前以 `calibrated_market_value` 汇总权重；持仓页面则优先以 `shares × 最新净值` 计算当前市值。建立同一份带估值日期的持仓快照供页面、工具和复盘使用。没有可信净值时可使用校准值，但必须显示其校准日期与降级状态，不能把校准值称为今日市值。
2. 检查 `/advice/portfolio` 与 `/{fund_code}` 的路由匹配顺序，保证组合接口确实返回组合数据。组合市场环境的查询也必须限定 `user_id`，并补相应回归测试。
3. 当前 `FundNav` 等历史记录并未完整保存数据源和抓取时间。新采集记录应写入来源与抓取时间；旧记录无法确定来源时标为 `unknown`，不得推断为 AKShare 或假装具有可追溯来源。
4. 复盘的“上次判断”以同一用户最近一次**成功完成的持仓复盘**为准，不以普通聊天摘要、单基金建议或失败的分析任务替代。

## 3. 用户体验与报告契约

### 3.1 入口和页面

- 提供“持仓复盘”入口，由用户手动发起；在 AI 对话中提出等价问题时进入同一 Skill。
- 报告页展示本次状态、三个关注位置、与上次相比、证据及数据限制；支持查看历史复盘。
- 每个关注项包含：标题、重要性说明、当前证据、与上次的关系、下一步观察条件。可以标为“风险”“变化”“待核实数据”或“保持关注”。
- 关键数据和判断使用可点击的证据引用。持仓、建议和历史报告页面需要支持带参数的直达与定位。

### 3.2 三件事的选择原则

Agent 先提出候选关注项，再按持仓影响、变化幅度、风险紧迫性、用户已确认的偏好和证据质量选择最多三项。服务端校验每项的证据与数据状态。不得因固定展示三个位置而编造三项风险；有效关注项不足三项时，剩余位置明确显示“暂无更多有证据支持的新变化”。

单基金的动作、目标仓位和置信度仍以有效的规则决策产物为准。组合复盘可以说明集中度、变化和观察条件，但在尚无组合级规则裁决时不由 LLM 自行计算具体调仓比例。

### 3.3 “与上次相比”的语义

比较基于结构化复盘记录，至少区分：

- **持仓变化**：基金增删、份额或权重变化；
- **数据变化**：净值、市场环境或其他有时间标记的数据发生变化；
- **规则变化**：规则建议、数据质量状态或规则版本变化；
- **判断延续**：关键证据未出现足以改变判断的变化。

每个变化引用本次与上次的证据和时间。首次复盘显示“暂无上次判断可比较”。同一天重复复盘仍可与前一次成功复盘比较，但显示两次运行的具体时间；数据未变时不能仅因模型措辞不同声称市场判断发生变化。

## 4. Agent 运行设计

```text
读取用户上下文与持仓快照
  → 加载持仓复盘 Skill
  → AI 提议取数计划
  → 服务端验证工具、参数、用户权限与总预算
  → 执行工具并生成证据
  → 数据质量门检查，必要时有限补查
  → 读取并比较上一次成功复盘
  → 生成结构化关注项与解释
  → 校验证据引用和规则结论
  → 持久化报告，流式展示结果
```

### 4.1 Skill

在 `backend/app/agent/skills/portfolio_review/` 建立版本化的 `SKILL.md` 和必要的输出契约。Skill 定义触发条件、允许使用的工具、必需数据、补查条件、关注项选择准则、降级路径、输出字段和示例。Skill 是应用运行时显式加载的业务流程；不能只把文件放在仓库里而不接入 Agent 服务。

优先复用 `get_portfolio`、`get_market_overview`、`get_latest_advice` 和 `compare_funds`。按需提供带当前估值的组合快照、用户偏好及上次复盘查询工具；单基金净值、板块趋势等作为补查工具。所有工具都从服务端身份获取 `user_id`，不能接受模型传入的任意用户 ID。

### 4.2 规划与预算

保留现有计划校验、工具白名单、超时和质量门。改造目前“同一计划中同名工具只允许调用一次”的限制，以步骤 ID 区分不同参数的只读调用。预算对**整次运行**计数，建议初始上限为 10 次工具调用、最多 2 次由质量门触发的补查；开发时用真实场景校准，不允许每次重规划重新获得完整调用预算。受控写入工具不进入自动规划。

为 `portfolio_review` 定义明确的数据质量要求。净值是否及时应结合实际公布时间和交易日历判断；周末、节假日不得简单按自然日或周一至周五推断。关键数据缺失或过期时输出降级报告，说明仍可确认的事实与无法作出的判断。

### 4.3 回答结构与一致性

模型先产生结构化的 `PortfolioReviewResult`：`status`、`as_of`、`findings`、`changes_since_previous`、`limitations`、`evidence_ids` 等。前端从结构化字段渲染卡片，避免只能从自由文本中解析三件事。每项实质性结论至少引用一条有效证据。结论中的具体操作不得与 `DecisionArtifact` 冲突；质量门降级时不得出现新增目标仓位。

## 5. 工具结果与证据契约

在现有 `ToolResultEnvelope` 上补充或关联以下字段：

| 字段 | 用途 |
| --- | --- |
| `source` | 数据来源或 `unknown`；区分数据库记录的原始来源与本次读取工具 |
| `as_of` / `fetched_at` | 数据代表的时间、本次取数时间；组合结果中的不同数据项保留各自时间 |
| `unit` / `calculation_basis` | 百分比、小数、市值、净值及计算口径，避免跨工具误读 |
| `evidence_id` | 本次复盘内稳定的证据标识，用于结论引用和页面定位 |
| `status` / `quality_flags` | 成功、部分、缺失、过期、失败及原因 |

为关键工具定义输出 schema，限制返回记录数和字段。保存报告时保留用于结论的最小必要数据快照、来源、时间、规则版本及证据映射；证据 ID 不只指向将来可能变化的“最新数据”页面。前端链接负责导航，保存的快照负责解释历史结论。

## 6. 记忆与数据模型

### 6.1 用户偏好

新增用户级偏好记录，第一期只支持风险偏好、投资期限、关注目标及必要的自由文本备注。字段具有来源、确认时间和版本。用户可查看、修改、删除；模型可以提出待确认的偏好，但不能仅从一次聊天自行写入长期记忆。未设置的偏好保持“未知”。

### 6.2 历史判断

新增 `PortfolioReview` 持久化记录，至少包含：`id`、`user_id`、状态、运行与数据时间、持仓快照、上次复盘 ID、偏好版本、Skill / Prompt / 规则版本、结构化结果、证据快照、质量报告和错误信息。报告按用户隔离，只有成功且数据契约完整的复盘可成为下一次比较基线。普通 `AgentConversation.summary` 继续用于会话衔接，不承担历史判断的权威来源。

运行状态写入数据库；服务重启后用户仍可读取已完成报告，并能识别中断的运行。第一期允许用户重新发起中断任务，不要求恢复执行到中断前的工具步骤。

## 7. 分步实施与验收

| 顺序 | 实施内容 | 可验收交付物 |
| --- | --- | --- |
| 1. 定义结果与失败案例 | 固定报告结构、三项选择准则、比较语义；扩展 `backend/evals/`；修正第 2 节的数据口径与组合接口问题 | 评测 fixture、回答样例、关键接口回归测试 |
| 2. 统一工具契约 | 增加来源、时间、单位、证据 ID、关键工具输出 schema；保存最小证据快照 | 任一关键数字可追溯到记录和实际日期 |
| 3. 实现持仓复盘 Skill | 接入 Skill 加载与版本，支持有界重复只读调用、质量门补查和结构化输出 | 正常、补查、降级三条路径均可完成 |
| 4. 加入记忆 | 用户偏好管理、复盘记录和上次判断检索；增加数据库迁移与用户隔离测试 | 偏好可控，跨会话比较准确，跨用户访问被拒绝 |
| 5. 完成前端体验 | 入口、报告、历史、证据链接和“与上次相比”区域 | 用户能从关注项打开证据并回看比较基线 |
| 6. 真实问题评测 | 匿名化问题集、运行轨迹、人工评分与回归报告 | 安全与正确性门槛全过，记录可用性基线 |

## 8. 评测方案

在现有固定日期离线评测基础上新增复盘用例，并保留原有用例。至少覆盖：正常多基金、单基金、空持仓、首次复盘、无新变化、持仓增删、同日重复、节假日、净值过期、建议缺失、工具失败、数据矛盾、偏好修改、规则版本变化及跨用户访问。

必须满足的硬门槛：

1. 不把过期净值描述为今日净值，不编造持仓、价格、收益或来源。
2. 每项实质性关注点都有有效证据；时间、单位和来源与证据一致。
3. “上次判断”仅取同一用户的成功复盘；首次复盘处理正确。
4. 操作与目标仓位不得越过规则决策和质量门。
5. 用户无法读取他人的偏好、持仓、复盘和证据。

再建立一组匿名化真实问题，检查工具选择、补查是否必要、三项内容是否有用、变化解释是否准确、用户能否确定下一步观察什么。首次运行先记录基线与典型失败；可用性数值门槛在看过基线后预先锁定，不依据后续结果临时调整。离线 fixture、真实模型和前端端到端检查分别报告，不能用离线规划通过率替代最终回答质量。

## 9. 第一阶段完成标准

- 用户可手动发起复盘，页面刷新后仍能查看运行状态或已完成报告。
- 报告最多给出三项有证据的关注点，明确各项数据的截至时间及限制。
- 第二次复盘能与上次成功复盘比较，并解释判断变化对应的持仓、数据或规则变化。
- 用户偏好由用户确认和管理；当前持仓与行情每次从可信业务数据读取。
- 关键数据质量、规则结论、证据引用和用户隔离通过上述硬门槛及集成测试。
- 前端可从报告打开对应持仓、建议和历史复盘；后端原有测试与 Agent 离线评测保持通过。
